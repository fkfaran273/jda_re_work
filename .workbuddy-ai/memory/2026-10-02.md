# 2026-10-02 — iOS adj9 verified: same algorithm, header law solved, one gap = claims bytes

## What the iOS capture proved (30 signed requests, cainiaot1iosmodd_24aug26 SAZ,
Cainiao iOS 5.8.0, `ios-simulator` build, consent.adjust.com/.io)

**The adj9 algorithm is shared with Android end-to-end** (9 subagents, all reports in
`adj9sign/one_click_run/_sub_*_RESULT.md`, consolidated verdict in
`adj9sign/IOS_VERIFICATION.md` rev 4):

- **Envelope identical**: 192 B = 16 header + 176 body, `algorithm="adj9"`,
  `adj_signing_id=1500000`, `headers_id=10`, `native_version=5.0.0` — 30/30.
- **`adj_verification` SOLVED**: `BASE64(cycle19("Quoh8uafohgh7CahM2h") XOR {"os_name":<os>})`.
  Key is **19 bytes cycled** (the "21-byte" reading was key + 2 bytes of its own repeat —
  only the 27-B ios-simulator value disambiguates). android → `KlcAG2cbAAsKSl1KVi0FGiJbDHMI`;
  **real device `{"os_name":"ios"}` → `KlcAG2cbAAsKSl1KXiwSSjA=`**; this capture (simulator)
  → `KlcAG2cbAAsKSl1KXiwSRT5bBSQZDhxXB0Mb`.
- **iOS header law SOLVED (28/28 + uniqueness ±1 day)**:
  `x = sec mod (2^31-1) (0→1); D[k]=16807·D[k-1] mod (2^31-1) k=1..8 (MINSTD, POST-step
  draws); w_i = D[2i]^D[2i+1]; BE32`. Only the generator differs from Android (bionic
  TYPE_3 vs MINSTD Lehmer); composition identical. Trap: pairing uses draws 1..8, NOT
  d[0]=x. Trap 2: Apple/FreeBSD `do_rand` wraps every call in `(ctx mod 2^31-2)+1` — the
  iOS lib uses the RAW Lehmer step, no wrappers (that's why earlier Apple-rand tests failed).
  Signing second ≈ request second (21×0, 3×+1, 2×−1, 1×−2, 1×−9).
- **Body cipher/digest/record shared**: `whiten_inverse` (14-round SPN, built from the
  Android signer) unseals 30/30; digest MAC (secret K) verifies 30/30; record constants
  (magic `01 00 08`, SHA256("")@79..110, `0e`×14 tail) 30/30; region(S) reproduces the d0
  head 30/30 with **selector phase (0x40,)** vs Android (0x2B,0x48).
- **3 iOS record deviations**: byte112=`0x02` (Android `0x01`); D9 cert slot = **20 zero
  bytes** (no APK cert concept on iOS); 16-B field @114..129 = device name
  `"iPhone13,2"` zero-padded (Android: zeros).
- **BINARY-LEVEL PROOF** (public `adjust/adjust_signature_sdk` v5.0.0, binaries in
  `adj9sign/core_bins/`): AAR libsigner.so sha256-identical to our reversed reference;
  iOS arm64 slice carries the SAME secrets — KB 240 B = Android KB XOR 0x55 (481-site
  unrolled block), IV2 XOR-0xCCCC, digest-key dwords plain, SHA256 IV/K XOR-0xCC.
  Same cipher, same obfuscation family.
- **iOS claims input structure** (public ios_sdk v5.8.0 source, `ADJRequestHandler.m`
  L582-639): core signs TWO maps — #1 wire params + send-time params (sent_at,
  queue_size, retry_count, first/last_error, wait_*), #2 extraParams {client_sdk,
  activity_kind ("click" not "sdk_click"!), endpoint (full URL), control_params};
  **the wire body is the core's OUTPUT (outputParams minus exceptionKeys
  {secret_id, signature, headers_id, native_version, algorithm, adj_signing_id}) —
  NOT the signing input**. Core picks os_name itself (ios vs ios-simulator) and
  holds a `frida-gadget` anti-tamper string (→ prefer SDK-source patch over
  FridaGadget if instrumenting).
- **/event claims law PROVEN** (Android frida traces, 91/91 block oracle + 27/27 full
  mints; mirrors to iOS keys): `event_count, event_token, partner_params` sorted into
  PROFILE **before** pinned id; `seq` into tail **after** it; serialization unchanged.
- **`mint_ios()` exists and works** (`_sub_ios_mint.py`): every record byte except the
  32-B BLOCK is byte-exact 30/30; full-blob 0/30 pending claims.

## The ONE remaining unknown — iOS claims payload (the 32-B BLOCK)

- ~93M hypotheses across 3 search generations (final oracle corrected) — 0 matches.
- **Two harness bugs found & fixed** (silently invalidating earlier negatives):
  (1) `oracle_batch` zero-filled mixed-length batches → extra zero blocks digested
  after short claims' length fields — use `_sub_claims3_oracle_fixed.py` for ALL
  future BLOCK searches; (2) regex `\r` leaked into authorization values.
- Decoded core string pool gives the real claim keys (signature, algorithm,
  adj_verification, authorization, environment, network_payload, os_name, bundle_id,
  idfv, app_version[_short], secret_id, client_sdk, activity_kind, endpoint,
  control_params + 5 Android-law constants) — still zero hits.
- **Ranked remaining hypotheses**: (1) **App-Store-receipt-derived claim bytes** — core
  parses the receipt in-binary (PKCS#7 OIDs embedded); receipt never on the wire ⇒
  unrecoverable from any capture, AND the server can't see it either ⇒ server can only
  do consistency checks (same structural argument as the Android TEE/key2 analysis);
  (2) `secret_id` = per-app constant baked in the closed core (control-flow flattened,
  dispatcher @0x6a370 — key order not statically provable); (3) exotic serialization (low).
- **Classification** (`_sub_ios_claims_law_RESULT.md`): per-install/generate-fresh
  (idfv, idfa, dedupe tokens, counters, timestamps, att_status, SKAN…) vs constants
  vs ONLY the 32-B claims bytes unknown.
