## Algo summary (inherited from earlier derayah work)
Java `HmacSHA256` over `HashMap.toString()` of the full activity-param map, key = non-exportable
AndroidKeyStore HmacSHA256 key alias `key2` (RSA-wrapped copy in SharedPreferences
`adjust_keys`/`encrypted_key`); `nSign()` then goes out to keystore2/keymint over binder and
returns a non-deterministic 176-byte blob → Base64 NO_WRAP → `Authorization: Signature
signature="...",adj_signing_id="...",algorithm="adj9",headers_id="...",native_version="5.0.0"`.

## Traps confirmed here
- Whole-dex single-byte XOR sweeps for `adj9` give false hits inside a MathJax HTML entity
  table in `classes7.dex` (yields adj0..adj9 for free). Always verify the containing table.
- `libsigner.so` `.rodata` has a second, per-build alphabet-scrambled string layer
  (`SAFWKGOAP`, `KJJAGPMKJ`) that is not Caesar/XOR/case-toggle — unrecoverable statically.

## CORRECTION (javap on the real 5.0.0 classes.jar) — earlier report was 3.x-shaped
Disassembled `com.adjust.sdk.sig.{Signer,u2,NativeLibHelper,t1}`:
- v5 canonical = `LinkedHashMap out = new LinkedHashMap<>(activityParams)` →
  `out.put(globals)` → `out.put("adj_verification", …)` → `t1.a(ctx, out.toString()
  .getBytes(UTF-8))`. So it's LinkedHashMap.toString(), but the PREFIX is a copy of
  the SDK's source HashMap → still bucket order. Both halves needed.
  `adj_verification` is inserted BEFORE the HMAC (part of signed input).
- Header is SIX fields in this fixed order (from `String.format("Signature
  %s,%s,%s,%s,%s,%s")`, each `%s=\"%s\"`): signature, adj_signing_id, headers_id,
  algorithm, native_version, adj_verification. 3.x had 5 fields, no
  adj_verification, algorithm before headers_id → my earlier findings file was wrong.
- Real entry points for frida: `Signer.sign(Context,Map,Map,Map)` (v5),
  `NativeLibHelper.a(Context,LinkedHashMap,byte[],int)` → private native
  `nSign(Context,Object,byte[],int)`; HMAC = `t1.a(Context,byte[])`; key mgmt = `t1`.
- Added `adj9/verify/HM2.java` + `verify_v5.py`: 30/30 vs JVM for the v5 path.
- Files corrected: `adjust-sig-findings.md`, `adj9/README.md`, skill §4/§5b.

## CORRECTION #2 — the #1 correction above was itself WRONG (header field order)
Re-read the array properly. `algorithm` comes BEFORE `headers_id` in 5.x too —
same as 3.x. 3.x differs ONLY by omitting `adj_verification`. Verified two ways:
- ref AAR 5.0.0 `u2.a(LinkedHashMap,byte[])`: slots 0=native_version 1=signature
  2=adj_signing_id 3=headers_id 4=algorithm 5=adj_verification; final array
  [0]=1 [1]=2 [2]=4 [3]=3 [4]=0 [5]=5.
- app `classes3.dex` `u2.a` @0x36a97c: `filled-new-array/range {v14,v15,v16,v17,v18,v19}`
  = signature, adj_signing_id, algorithm, headers_id, native_version, adj_verification.
Trap: javap register slots are REUSED, so `aload 4` next to `ldc algorithm` does not
mean "4th field". Name every slot first, then read the array. Fixed in
`canonical.py:build_authorization_header`, findings, README, skill.
